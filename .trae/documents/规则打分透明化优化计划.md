# 规则打分透明化优化计划

## Summary

当前规则概览对用户来说是黑盒：硬性淘汰规则的 `detail` 是静态字符串，不显示当前阈值和来源；打分结果虽然存了 `hard_checks`（含 hit/confidence/evidence），但职位详情页完全没展示；维度封顶 10 分的陷阱也没提示。本次优化解决这三个核心问题，让用户能清楚看到"每条规则是怎么判的、这个职位实际命中了什么"。

## Current State Analysis

### 问题 1：硬规则 detail 是静态字符串，不显示当前阈值
- 文件：`gaj/core/scoring.py` 第 909-921 行 `_CATALOG_STATIC["hard_checks"]`
- detail 是写死的描述，如 H-03 写"默认 20 人"，但 20 来自 `profile.reject_scale_below`，用户改了画像后 detail 不会同步
- H-05/06/08 的 detail 提到"证据置信度低于阈值只标 REVIEW"，但没说置信度从哪来（JD 信号推断）

### 问题 2：职位详情页不展示 hard_checks 命中证据
- `ScoreResult.to_dict()` 第 162 行已经序列化了 `hard_checks`（含 hit/confidence/evidence/fatal 字段）
- `rule.json` 里已经存了完整的 hard_checks 数据
- 但 `index.html` 第 375-404 行的规则打分区块只展示了：status、total_score、dimension_scores、reject_reason、warnings、triggered_ai_rules
- **完全没有展示 hard_checks**——用户看不到"哪条规则命中了、证据是什么、置信度多少"

### 问题 3：维度封顶 10 分不可见
- `DimensionScore.finalize()` 第 86 行 `min(raw, self.max_score)` 硬封顶 10
- `build_rules_catalog` 第 1000 行 `dim["max_score"]` 是各项 max 之和，可能 >10
- 前端 `dimMaxSum(dim)` 显示的是编辑中的求和值，但实际打分会被截断
- 用户调高单项 max 后以为能得更高分，实际被静默截断

## Proposed Changes

### 改动 1：硬规则 detail 动态化 + 显示阈值来源
**文件**: `gaj/core/scoring.py`
**位置**: `build_rules_catalog()` 函数（第 977-1002 行）

**做什么**:
1. 给 `build_rules_catalog` 加一个可选参数 `profile: Profile | None = None`，默认 `None` 时加载
2. 在构建 hard_checks 时，动态注入当前画像里的阈值到 detail 字段
3. 每条硬规则增加 `threshold` 字段（结构化数据，不是塞进 detail 字符串）：
   - `value`: 当前阈值（如 20、30.0、["北京","上海"]）
   - `source`: 画像字段名（如 `profile.reject_scale_below`）
   - `source_label`: 中文字段名（如"拒绝规模下限"）
   - `editable_in`: "画像编辑"（提示用户去哪改）

**具体硬规则的 threshold 注入**:
| 规则 | threshold.value | threshold.source | threshold.source_label |
|------|----------------|-----------------|----------------------|
| H-01 | `profile.all_acceptable_cities()` | `profile.acceptable_cities + current_city` | 可接受城市列表 |
| H-02 | `profile.reject_industries` | `profile.reject_industries` | 拒绝行业列表 |
| H-03 | `profile.reject_scale_below` | `profile.reject_scale_below` | 拒绝规模下限(人) |
| H-04 | `profile.hard_min_salary_10k` | `profile.hard_min_salary_10k` | 硬性最低年薪(万) |
| H-05 | `not profile.accept_travel` | `profile.accept_travel` | 是否接受出差 |
| H-06 | "JD信号推断(overtime==heavy)" | `job.signals["overtime"]` | 加班强度信号 |
| H-07 | `profile.blacklist_keywords` | `profile.blacklist_keywords` | 排除关键词黑名单 |
| H-08 | `not profile.accept_outsourcing` | `profile.accept_outsourcing` | 是否接受外包 |

4. 同时改进 detail 文本，补充置信度机制说明（对 H-05/06/08）：
   - H-05: "JD 要求长期驻场/外派, 且画像明确不接受出差。**判定逻辑**: 命中后取 JD 信号推断置信度, ≥floor 直接淘汰, <floor 标 REVIEW 交 AI 核实。"
   - H-06: "推断为 996/大小周等高强度作息。**判定逻辑**: 置信度来自 `job.signals["overtime"]`, ≥floor 直接淘汰, <floor 标 REVIEW。"
   - H-08: "推断为外包/驻场岗位。**判定逻辑**: 置信度来自 `job.signals["outsourcing"]`, ≥floor 直接淘汰, <floor 标 REVIEW。"

**为什么**: 用户看到"当前阈值是多少、来自画像哪个字段"后，就知道去画像编辑里改。硬规则阈值保持在画像里编辑（用户选择"只展示来源"），不在规则 tab 重复。

**怎么做**:
```python
def build_rules_catalog(
    overrides: ScoringOverrides | None = None,
    profile: Profile | None = None,
) -> dict[str, Any]:
    import copy
    from .profile import load_profile

    ov = overrides or _load_active_overrides()
    prof = profile or load_profile()
    catalog = copy.deepcopy(_CATALOG_STATIC)
    # ... 现有逻辑 ...

    # 动态注入硬规则阈值
    for hc in catalog["hard_checks"]:
        hc["threshold"] = _build_hard_check_threshold(hc["code"], prof)
    return catalog
```

新增 `_build_hard_check_threshold(code, profile)` 函数返回 `{"value":..., "source":..., "source_label":..., "editable_in":"画像编辑"}`。

### 改动 2：职位详情页展示 hard_checks 命中证据
**文件**: `gaj/web/static/index.html`
**位置**: 第 375-404 行"规则打分"区块

**做什么**: 在 dimension_scores 展示之后、reject_reason 之前，插入 hard_checks 展示区块：
- 只展示 `hit == true` 的硬规则（没命中的不显示，减少噪音）
- 每条命中的硬规则展示：

```javascript
formatThreshold(t) {
  if (!t) return '';
  if (Array.isArray(t.value)) return t.value.join('、') || '(空)';
  if (typeof t.value === 'boolean') return t.value ? '是' : '否';
  return String(t.value);
}
```

### 改动 4：维度封顶 10 分前端校验
**文件**: `gaj/web/static/index.html` + `gaj/web/static/app.js`

**做什么**:
1. `dimMaxSum(dim)` 不变（还是算求和值）
2. 在维度头部增加超限提示：当 `dimMaxSum(dim) > 10` 时，显示红色警告"⚠ 超过封顶10, 实际最多算10分"
3. `saveScoringConfig()` 增加前端校验：如果任一维度 `dimMaxSum > 10`，阻止保存并 toast 提示

**HTML 修改** (第 98-101 行):
```html
<div class="dim-header">
  <strong x-text="dim.label"></strong>
  <span class="dim-max" :class="{'over-cap': parseFloat(dimMaxSum(dim)) > 10}"
        x-text="'当前满分 '+dimMaxSum(dim)+' / 默认 '+dim.default_max_score"></span>
  <span class="dim-cap-warn" x-show="parseFloat(dimMaxSum(dim)) > 10"
        style="color:var(--red);font-size:11px">⚠ 超过封顶10, 实际最多算10分</span>
</div>
```

**JS 修改** (`saveScoringConfig`):
```javascript
async saveScoringConfig() {
  // 校验维度封顶
  for (const dim of this.rulesCatalog.dimensions) {
    const sum = parseFloat(this.dimMaxSum(dim));
    if (sum > 10) {
      this.toast(`${dim.label} 各项满分之和 ${sum} 超过封顶 10, 请调整后再保存`, 'error');
      return;
    }
  }
  // ... 原有保存逻辑 ...
}
```

**CSS**:
```css
.dim-max.over-cap { color: var(--red) !important; }
```

**为什么**: 用户选择"强制不超10"。前端阻止保存比后端静默截断更透明——用户能立即知道哪里超了，而不是保存后打分时被静默截断。

## Assumptions & Decisions

1. **硬规则阈值保持在画像里编辑**（用户选择"只展示来源"），不在规则 tab 重复编辑入口
2. **hard_checks 命中证据展示在职位详情页**（用户选择"触发条件+实际命中证据"），rule.json 已有数据，无需改后端存储
3. **维度封顶用前端校验阻止保存**（用户选择"强制不超10"），不改后端 `finalize()` 的 `min(raw, 10)` 逻辑
4. **detail 文本仍保留但补充置信度机制说明**，不删除——有些用户只看文本不看结构化字段
5. **不改 `scoring_rules.md` 文档**——文档已过时但本次不动文档，聚焦代码和 UI
6. **`_CATALOG_STATIC` 保留**——作为 fallback，动态注入是在 `build_rules_catalog` 里做的
7. **R-04 特殊资源**不在本次改动范围（用户没提到，且无 UI 入口注入加分是另一个问题）

## Verification Steps

1. **启动 Web 服务**: `python3 -m gaj web` → 打开规则概览 tab
2. **验证硬规则阈值展示**: 每条硬规则卡片下方应显示"当前阈值: XXX ← 来源字段" + "去画像编辑改"链接
3. **验证阈值动态同步**: 在画像编辑 tab 改 `reject_scale_below`（如 20→50）→ 保存 → 切回规则概览 tab → H-03 的阈值应显示 50
4. **验证职位详情页 hard_checks**: 点开一个 `status=REJECTED` 的职位 → 规则打分区块应展示命中的硬规则（红色淘汰标签 + reason + evidence）

7. **验证封顶正常保存**: 把各项 max 调回总和 ≤10 → 保存成功
